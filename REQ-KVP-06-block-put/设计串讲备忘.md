# REQ-KVP-06 设计串讲备忘

本文串联 `REQ-KVP-06` 与已有 KV、PD 和 Store 需求。正式流程、接口和测试以主设计文档为准。

## 1. 依赖与约束

| 需求 | 依赖内容 | 本需求使用方式 |
|---|---|---|
| `REQ-KVP-01` | GPU KV buffer 初始化和注册 | PutTask 使用已注册的 HBM 地址。 |
| `REQ-KVP-03` | Store 的 Put 封装、重连和失败降级 | worker 调用统一 Store client，不在 Scheduler 中处理后端细节。 |
| `REQ-KVP-04` | Prefix block 的分配和异步 Get 生命周期 | Put 与 Get 共用 block size、HBM 生命周期和 Engine poll 边界。 |
| `REQ-KVP-07` | Store 失败指标和重算 | Put 失败记录指标，后续请求按 miss 处理。 |

- `block_size` 使用 DeepInfer 的运行时配置。
- Store item 只能对应完整 block；未满尾 block 不作为独立对象写入。
- PutTask 必须保存 block ID 快照，不能异步读取已经可能被 `free_seq()` 清空的 `seq.cache.block_table`。
- `pin_blocks()` 和 `unpin_blocks()` 必须成对执行，失败、取消和 worker 异常也必须产生清理路径。
- `PutTask.kv_write_done_event` 是模型 KV 写入 stream 的完成事件，不是 Store completion；worker 等待它只保护 HBM 源数据一致性，不阻塞 Scheduler。
- Python worker 不直接修改 C++ `Sequence`、`block_table` 或 Scheduler 队列。
- PD 的 PE HBM 传输与 KV pool Store Put 是两条独立路径；未满 block 不写 Store 不代表 PD 可以忽略其传输或重算约束。

## 2. 主流程接入结论

- `pe_prepare_save_kvcache()` 在 `pre_sampler_sync()` 中负责 Prefill 保存资格判断、block 快照和 pin。
- `pe_do_save_kvcache()` 在 `LLMEngine.post_process()` 中提交 Prefill PutTask。该函数通过 `EngineCallbacks.post_process_fn` 由 driver worker 实际调用。
- `do_save_kvcache()` 在 Decode 的 `pre_sampler_sync()` 中处理上一轮已提交 KV，提交新形成的完整 block。
- `finalize_seq()` 只释放 request 引用；Put 引用由 completion poll 后的 `unpin_blocks()` 释放。
- `send_processed_prompts()` 保持 Prompt/PD 交接职责，不重复提交相同 Put。

## 3. 待确认事项

1. `pe_prepare_save_kvcache` 是否扩展为接收 `(Sequence, SequenceMetadata)`，或由
   `LLMEngine.step()` 先筛选最后一个 Prefill chunk；无论接口形式如何，中间 chunk
   不提交，最终完整 block 计算必须使用本轮目标 `seqlen_k`，不能使用执行前的旧
   `cache.num_tokens`。
2. Decode Put completion 是否复用现有 KV worker 线程，还是使用独立 Put 队列。
3. 多 rank 是否需要在本地 Put completion 之后发布逻辑 block 完成事件；本需求默认先释放本 rank 的 Put 引用。
4. Engine 在无推理请求但存在 pending Put 时的继续运行条件，需要与现有 Engine idle/退出逻辑统一。
5. Get 恢复后若 suffix 仍是 chunked Prefill，Put 的最终提交是否统一以
   `is_last_prompt_chunk` 和 `seqlen_k` 判定，避免在中间 chunk 重复 pin/Put。

## 4. 本需求暂不覆盖

- 未满尾 block 的独立 Store 对象写入。
- SWA state 的异步 Put、Get 和 replay。
- Store 端 LRU、TTL、容量和租户策略。
