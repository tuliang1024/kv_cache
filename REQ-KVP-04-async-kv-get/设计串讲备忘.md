# REQ-KVP-04 设计串讲备忘

本文用于串联 `REQ-KVP-04` 与相关需求，记录依赖、实现约束和当前遗留问题。正式流程和伪代码以主设计文档为准。

## 1. 依赖关系

| 需求 | 依赖内容 | 本需求使用方式 |
|---|---|---|
| `REQ-KVP-01` | PE/CE 初始化 Mooncake Store 并注册 KV Cache | worker 使用已注册的 `gpu_blocks` HBM region。 |
| `REQ-KVP-02` | PrefixMatcher 的 vLLM 兼容 hash/key 规则 | worker 根据请求 token、block size 和 rank 拓扑生成 key。 |
| `REQ-KVP-03` | Store 注册、`get`、失败降级和生命周期 | worker 提交逐 block item；Store backend 处理短读、重连和熔断。 |
| `REQ-KVP-05` | Router 透传请求级前缀命中数 | Scheduler 只消费命中 token 数，不规定上游数据结构。 |
| `REQ-KVP-07` | Store 失败、回退和命中率指标 | 记录 get 失败、连续有效前缀和回退结果。 |

## 2. 实现约束

- `block_size` 必须使用 PE `CacheEngine` 的运行时值，不得写死。
- 一个 Store item 应对应一个 prefix block，以保留逐 block 失败信息。
- Python worker 不得直接修改 C++ `Sequence`、`block_table` 或 Scheduler 队列。
- Store backend 的重连、重注册、分块、锁和熔断不进入 Scheduler 状态机。
- `kv_loading` 和 `kv_ready` 不得被 `get_sum_prompt_len_waiting()` 误报为可执行 Prefill。
- `get_num_unfinished_seqs()`、abort 和 finished 清理必须覆盖两个新增队列。
- 任一 DP rank 的加载结果不一致时，必须在 collective Prefill 前统一到相同的连续前缀。
- vLLM 的 `async_kv_waiting` 用于等待启动 load；启动后请求进入 `kv_holding_waiting`，该队列优先于普通 waiting。DeepInfer 将在途阶段拆为 `kv_loading`、完成阶段拆为 `kv_ready`，两者都不得追加到普通 waiting 队尾。

## 3. 当前遗留问题

1. `SchedulerOutputs.kv_load_tasks` 的 pybind 具体结构；需要保证 Python 转换前任务数据有效，且不借用下一轮复用的 vector。
2. `get_num_pendings()` 是否拆分统计 `waiting`、`kv_loading` 和 `kv_ready`，避免服务层把异步加载误报为可执行 Prefill。
3. ready 超时和内存压力阈值的配置入口；未确定前不写入固定数值。

## 4. 本需求暂不覆盖

- SWA state 的异步加载和 replay，属于后续 SWA 需求。
- Store 端 LRU、TTL 和容量策略，由 `REQ-KVP-03`、`REQ-KVP-09` 负责。
- CE 直接读取池化 Store，CE 仍按现有 PD KV transfer 方案工作。
